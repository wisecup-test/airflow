# Adoption of Standard random Module for Non-Cryptographic Randomization: Tooling Components Requiring Reproducible Sequence Generation

Date: 2025-05-15
Deciders: Detection Pipeline (automated)

## Scope Paths

Root: `dev`

Applies to:
- `breeze/src/airflow_breeze/**`

## Context

- Developer environment tooling and image build pipelines require transient values to invalidate build caches and handle non-deterministic automation helpers.
- Multiple build parameter construction and automation utility modules incorporate pseudo-random generation routines.
- Standard library pseudo-random algorithms provide built-in execution without adding external dependency overhead to the automation toolchain.

## Problem Statement

Developer tooling requires non-deterministic values for cache busting and operational helpers without introducing heavy third-party dependencies, while ensuring pseudo-random algorithms are strictly segregated from security-sensitive cryptographic pathways.

## Decision

- **R-LM-001** SHOULD: Tooling components requiring reproducible sequence generation SHOULD explicitly seed the random module state or provide deterministic fallback overrides.

## Policy Block

In scope:

- Developer environment automation and build parameter generation modules requiring transient pseudo-randomness
- Non-cryptographic cache invalidation and utility string generation

Out of scope:

- Cryptographic key generation, password hashing, and security token issuance
- Deterministic build processes requiring bit-for-bit reproducible build artifacts

Exceptions:

- **EXC-20-001** A task requires cryptographically secure unpredictability or secure secret generation
  Approval: Security architecture team review
  Documentation: Document the cryptographic requirement and use dedicated cryptographic modules

## Rationale

- The standard random module provides built-in pseudo-random number generation without introducing external package dependencies to the development tooling subsystem.
- Generating randomized indicator strings via random.randrange enables explicit, selective cache busting during build automation without altering underlying configuration schemas.
- Restricting random to non-cryptographic use cases maintains a clear separation between utility randomization and cryptographic security concerns.

## Consequences

Positive:

- Zero external dependency footprint for pseudo-random number generation across developer environment utilities.
- Straightforward cache invalidation through transient randomized indicator strings.
- Consistent random generation API across all build and release tooling modules.

Negative:

- Pseudo-random numbers generated by the module are predictable and unsuitable for security-sensitive operations.
- Unseeded pseudo-random generation can lead to non-deterministic execution in test and verification pipelines.

## Alternatives

- Adopting a dedicated cryptographic secrets module for all randomization needs (rejected)
  Rejected because: Cryptographic entropy sources introduce unnecessary overhead and complexity for non-security build cache invalidation and simple utility scripts
  When valid: When generating security tokens, session keys, or authentication secrets
- Using deterministic timestamps or monotonic sequence counters for build cache busting (rejected)
  Rejected because: Timestamps introduce false-positive cache misses on consecutive runs within the same build cycle and cannot provide isolated random indicators
  When valid: When strict chronological ordering of artifacts is required

## Risks

- Accidental use of the pseudo-random generator for security-sensitive tokens or password generation
  Mitigation: Static analysis checks and code review policies prohibiting pseudo-random functions in security-sensitive modules
  Owner: Engineering team
- Flaky test execution resulting from non-deterministic pseudo-random values in test suites
  Mitigation: Enforce explicit seed initialization or mock random calls within automated testing suites
  Owner: Engineering team

## Implementation Notes

- DISCOVERY POLICY (MANDATORY): This ADR omits all tool names, file names, commands, package managers, and version numbers. The consumer MUST derive them from the project repository.

LOCK-VERSION GROUNDING (MANDATORY) — before writing code that uses a versioned library, execute in order:
1. Find the dependency manifest in the repo. It declares ranges, not installed versions.
2. Identify the build tool from the manifest.
3. Inspect the repository lock or resolution artifact to determine the exact resolved version. This artifact is authoritative; build-tool output only verifies the active environment matches it.
4. Look up the official documentation, changelog, or public API reference for that exact version. Do not use training-data recall — fetch or search the public internet for version-specific docs.
5. Confirm every API, class, or function you will call exists in that exact version's documentation before using it.
6. For version-sensitive behavior, re-run steps 3-5 per dependency at point of use.
- When constructing cache-busting arguments, format random integer ranges into hexadecimal string representations.
- Ensure all security-sensitive flows are audited to prevent pseudo-random utilities from being imported into credential-handling pathways.

## Continuation Context

Verify commands:

- Discover and execute the project static analysis validation target to verify module import safety across development tooling.
- Discover and run the test suite covering build parameter generation and utility functions.

Accept when:

- Static analysis validates that pseudo-random generation APIs are confined to non-cryptographic modules.
- All test suites covering build parameter generation pass without non-deterministic failures.

## Enforcement

- Verified by: Automated code analysis and linting in continuous integration
- Verified by: Peer code review for changes affecting developer tooling and build parameter construction
- Violation handling: Pull requests introducing pseudo-random generation in security contexts are blocked from merging.
- Violation handling: Violations identified in code reviews must replace pseudo-random generation with appropriate cryptographic or deterministic alternatives.
- Exception process: Exceptions require documented justification detailing why non-standard randomization is necessary, approved by the architecture review team.
